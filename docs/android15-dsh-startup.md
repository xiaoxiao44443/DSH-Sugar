# DSH 冷启动与官方桌面端的对照

2026-11-07，DSH 0.2.2-rc.1，Android 15 ARM64 真机 PKR110。测试对象是已修复插件热加载的 DSH Sugar debug APK，SHA-256 为 `2179954856aea37db9be562e9557e2d305056e238bcbd721fcc5e0b7703064ab`。测试保留了已展开的镜像、用户配置和插件状态。

## 官方桌面端的启动顺序

同版本的 Electron 主进程先在隐藏窗口加载安装包里的 `dsh-app://app/`，再准备运行环境并启动 Host。Host 通过 IPC 发回就绪信息，已有网页继续初始化。主进程此时才选择显示欢迎页或工作区。窗口打开、后端监听、聊天可以操作是三个可分别测量的时刻。[主进程启动顺序](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.1/apps/desktop/src/main.ts#L641-L650)

桌面 Host 是独立的 Electron Node 模式子进程，仍通过共享的 `runProfile()` 加载桌面插件配置。已存在的子进程会复用同一个就绪结果。用户确认关闭到后台后，普通关窗保留窗口和后端，再次打开可以直接恢复；明确退出才走关闭流程。本次没有同口径的 Windows 冷启动数字。[Host 进程及 IPC](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.1/apps/desktop/src/host-process.ts#L191-L235) · [共享 profile 入口](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.1/apps/desktop-host/src/index.ts#L18-L44) · [窗口生命周期](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.1/apps/desktop/README.md#closing-the-window-and-quitting)

桌面安装包的 `app.asar/dsh` 提供固定的生产依赖。外部插件由用户的桌面 profile 独立管理。Sugar 也已随 APK 提供固定依赖，在这次测量中没有解包或安装依赖。两端目前的区别包括读取安装资源的路径、Host 的运行环境，以及网页开始加载的时刻。[桌面端运行时与打包](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.1/apps/desktop/README.md#key-technical-decisions) · [Sugar 的客体镜像](../scripts/prepare-guest.py)

## Android 真机数据

原版进程被停止后重新启动，从发出桌面启动 Intent 到聊天输入框可见、可点击，五轮用时 **9.06、9.13、11.62、11.27、11.67 秒**，中位数 **11.27 秒**。WebView 从导航到输入框的中位数约 **1.05 秒**。每轮均在无输入草稿、无可见生成任务时开始，未发送消息，也未重启手机或清理系统文件缓存。

四轮临时加入 Node 计时探针后的首屏中位数为 11.29 秒。下表基于各轮同一个单调时钟计算阶段差，再分别取中位数。部分阶段互相包含。

| 阶段 | 中位数 | 四轮范围 |
|---|---:|---:|
| Node 首段 JS 到 DSH 发布可登录的 Web 地址 | **7.92 秒** | 6.70–9.21 秒 |
| 首次扫描安装镜像中的 581 个依赖包 | 0.60 秒 | 0.57–0.61 秒 |

每轮在交出地址前记录到 270 次 Loader 条目导入。各导入在时间轴上有大量重叠，它们占用的时间区间取并集后中位数为 6.03 秒。某插件等待了数秒也可能是在等与其他插件共享的依赖。HMR 每轮都在地址发布后才执行一次初始配置核对，耗时中位数 0.57 秒，与随后 WebUI 加载有重叠。

另两轮专门对同步调用计时。设备发出启动命令到 Node 首段 JS 分别约 1.53、1.44 秒，包括 Android Activity、环境准备、Sucrune 和 Node 引导。在 Loader 待就绪的 6.36、7.31 秒内，公开的同步文件 API 分别占 2.07、2.39 秒，Node 原生 ESM 解析占 1.70、2.10 秒。各计时桶扣除了嵌套调用。两轮均观察到 11,202 次原生 ESM 解析、11,475 次公开 `realpathSync` 调用和 5,854 次公开 `readFileSync` 调用。这些是函数调用计数，不能直接视为物理磁盘读取次数或 Sucrune 的独占成本。

另一轮只统计成功调用的重复度。按父模块、请求字符串和导入属性组合计数，11,202 次原生 ESM 解析对应 11,202 个不同组合，其中 9,698 个是相对导入。对内置 JS 文件的路径解析则是 8,617 次调用、2,434 个目标路径。安装目录下 2,493 次 JS 内容读取对应 2,493 个不同路径，2,608 次语言资源目录读取也对应 2,608 个不同路径；该分类包括 `locale/`、`locales/` 中的 JS 和 JSON。另有 656 次包清单读取对应 202 个路径。由此可优先评估减少发行包内分散的小模块、复用单次启动中已解析的固定路径。仅按完整 ESM 请求键缓存，在这一轮没有可重复利用的原生解析调用。

对 APK 本身检查还发现 57 份 `zod@4.4.3`。每份的 508 个文件按相对路径和内容 SHA-256 核对一致，镜像另有一份 `4.6.7`。这是适合单独做打包实验的候选。现有手机探针只记录目录类别，不能将全部 2,608 个路径都归给 Zod。直接合并同版本的多个模块实例也会改变导出对象和类的身份，必须同时验证插件隔离、跨包类型检查和语言切换。

## 一个已验证的优化边界

本次从固定 APK 镜像生成了安装依赖索引。在真机上逐项比对包名、目录、声明方和版本，顺序和值均与 DSH 的实时扫描一致。临时仅给本次进程的首次安装图查询使用该索引，三轮该阶段为 **2.0、1.7、2.5 毫秒**。同组三轮聊天输入框可用耗时为 **12.04、11.71、9.51 秒**，波动大于该项节省，尚不能据此认定首屏已加快。产品化需要按镜像及实际安装资源校验，保留用户插件、跳过损坏包与热加载的动态解析。

## 手机版可借鉴的部分

1. **缩短冷启动后的网页准备。** 本节所测原版 Activity 在验证动态端口并写入登录 Cookie 后才创建 WebView。小步实验可以在原生启动页首帧之后创建空白 WebView，等本轮端口通过验证再导航。若按桌面端做成同一张页面从启动一直用到聊天，则需要让 APK 提供可信的静态入口，并为该页面设计就绪交接、认证和 HTTP/WebSocket 的同源访问。前一轮测到单纯创建 WebView 约 43 毫秒。完整网页导航的约 1 秒中，能提前完成的比例还需 A/B 验证。[Android 入口](../app/src/main/kotlin/app/dsh/sugar/MainActivity.kt) · [本地登录](../app/src/main/kotlin/app/dsh/sugar/runtime/SugarRuntime.kt) · [先前测量](android15-startup.md)
2. **缩短 Host 真正可用的时间。** 优先减少内置模块的路径查询和重复读取。在同一轮解析中复用已解析的目录，或对 APK 自带、版本可验证的资源建立索引，并把外部插件及可变工作区留给动态解析。应以聊天可用和插件热加载均正常为验收条件，同时观察 Loader 独占各项的变化。
3. **分开验证暖返回。** Sugar 已在进程内复用 Host，Activity 和 WebView 也还驻留时可直接回到原聊天页。之前同机按 Home 后返回的中位数约 80 毫秒。Android 回收进程后仍要走冷启动，因此后台保活与本次冷启动优化应分别衡量。[原始暖返回数据](android15-startup.md)

## Sucrune 文件调用与冷启动对照

Android 15，PKR110，沿用该机已经展开的 DSH 安装目录。在同一个应用 UID 的原生进程和由 DSH Node 通过 Sucrune fork/exec 启动的客体子进程中，分别运行同一份无 libc 的 ARM64 ELF。它从应用私有安装目录中选取 72 个文件，覆盖 JS 模块、包清单和语言资源。两端逐个核对文件大小、内容前缀指纹，再比对 inode 汇总指纹。计时在程序内部进行，包含请求与返回，不含启动 ELF 的时间。每个 APK 内原生与客体各 5 轮交错，每轮每种操作 1,296 次，系统文件缓存已预热。逐级查询按文件路径计一次，内部包含多次系统调用。

| 操作，每次中位数（微秒） | 原生，原版对照 | Sucrune 原版 | 原生，新版对照 | Sucrune 新版 |
|---|---:|---:|---:|---:|
| 单次 getpid | 0.13 | 2.43 | 0.13 | 2.02 |
| 查询已有文件 | 1.35 | 60.59 | 1.31 | 48.25 |
| 查询缺失文件 | 1.17 | 67.07 | 1.12 | 40.01 |
| 打开后关闭 | 2.16 | 138.56 | 2.24 | 101.31 |
| 打开、读取最多 4 KiB、关闭 | 2.58 | 200.33 | 2.81 | 188.38 |
| 逐级检查一个完整路径 | 7.42 | 427.45 | 6.02 | 424.00 |

Sucrune 在 ARM64 上直接执行指令。对项目文件的 Linux 调用经过系统调用翻译和管理进程的文件代理（broker）。改动在遍历中间目录时使用内核一次性检查目录类型、禁止跟随链接，并保留已打开的目录描述符继续查找。每个普通中间目录省两次宿主 fstat。遇到中间链接会多一次失败的目录打开，再走原有链接解析。测试中的 getpid 没有经过修改过的路径代码，其两组客体结果也有 17% 波动。客体子进程与主 Node 的系统调用入口有所不同，表中比值不能换算为 DSH 首屏慢多少倍。

基准中 Node 的 execFileSync 曾抛出 ENOTSOCK，当时异常携带的子进程输出已含完成标记。两版共 20 份计时记录均具有完整的 6 组结果、迭代计数和结果指纹。尚未确定触发错误的系统调用或其对日常 DSH 的影响。

## 主 Node 的 realpath 与文件代理往返

同一台 Android 15 手机，Node 24.22.2。下面的计数从 DSH 主进程第一段加载脚本开始，到发布可登录地址为止，覆盖应用启动和 Cordis 装配。计数、调用栈、函数计时、代理报文计数和整机冷启动分别测量。旧版指上一节最终交付的 APK，SHA-256 以 8effb7c4 开头。

* Node 完整命中内部路径缓存的安装 JS 查询有 6,410 次，触发 0 次底层 lstat，计时轮合计约 59 ms。另有 5,139 次未命中完整路径，其中间目录仍可命中缓存，共触发 6,314 次 lstat，计时轮合计约 554 ms。
* DSH 的 compileResolution 为 581 个安装条目各做两遍未缓存的目录解析，两处各触发 2,740 次 lstat。有两个包目录名称以 .js 结尾，单看文件名后缀会漏计这两条。另有 581 次 realpathSync.native 来自安装包图扫描，计时轮约 171 ms。
* 在独立诊断 APK 中，用同一文件代理会话的开始和结束标记直接计数请求。三轮均得到相同结果。对安装入口 /opt/dsh/node_modules/@deepseek-ai/dsh/lib/bin.js，未传缓存的 realpathSync 每次发出 7 次 fstatat，.native 每次发出 7 次 readlinkat。对该包目录分别为 5 次 fstatat 和 5 次 readlinkat。空区间为 0 次，单一 lstat 对照为 1 次 fstatat。这两个无链接实例的数值不能套用到带缓存或含符号链接的路径。

新 DSH 在没有链接插件目录时省去安装目录前缀的物理路径计算。有链接插件时，每个安装条目解析一次并复用结果。用户 profile 按原行为保存其真实路径，更新路由时重新处理链接，只有发生过路径迁移才去清理旧映射。主 Node 的公开 JS/native realpath 入口由 13,354 次降至 12,192 次，其内的底层 lstat 由 11,902 次降至 6,422 次（减少 5,480 次，46.0%）。独立计时轮的所有这些 realpath 调用累计约 911 → 786 ms，每版各一轮。Host 和 Worker 均通过含真实目录链接的路由回归，覆盖同名包、链接迁移、目标缺失后恢复以及热替换限制。[打包的 DSH 补丁](../guest/profile-resolution.patch)

Sucrune 的主 Linux runner 现在按当前映射页验证路径参数的可读性，读取遇到 NUL 字节即停止。基础内置程序仍逐字节校验。4 KiB、16 KiB、页末 NUL、下页不可读等共 52 项宿主差分用例通过。同一主 Node、6 个实际安装文件、每版 2 个进程各 5 批、每批每种调用 288 次，未传路径缓存时 JS realpath 中位数 594 → 577 µs，native 为 548 → 536 µs。样本范围重叠。四个进程均核对了返回路径、相对链接和悬挂链接的 ENOENT。

## DSH 0.2.2-rc.3 的插件启动耗时

2026-11-14，同一台 Android 15 PKR110，保持并行启动、原生启动页、现有插件和用户配置。每轮停止应用进程后从桌面入口启动，保留系统文件缓存。后端耗时从 Sugar 请求启动 DSH 到 Sugar 发现可登录地址，整机耗时从发出启动 Intent 到输入框可见并可操作。后端发布地址、App 发现地址、完成本地认证是三个分别计时的事件。

### 一次 5.447 秒的启动

| 顺序 | 本轮耗时 |
