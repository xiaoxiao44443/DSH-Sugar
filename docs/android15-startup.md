# Android 15 真机启动耗时

2026-11-07，PKR110，ARM64，系统 WebView 156.0.8078.47。测试的是 DSH Sugar 的 Android debug 版。日常启动保留了手机原有的工作区、模型配置和语音插件。以下数值为这台手机的实测结果，单位为秒。

当前插件热加载版的后端分段、依赖索引实验和官方桌面端对照见[DSH 冷启动与桌面端](android15-dsh-startup.md)。

## 用户要等多久

| 情形 | 次数 | 计时终点 | 中位数 | 最短–最长 |
| --- | ---: | --- | ---: | ---: |
| 原版，进程被停止，Linux 镜像已经展开 | 5 | 聊天输入框可见、可接受点击 | 11.16 | 8.12–11.82 |
| 原版，按 Home 后很快重新点桌面图标；进程、页面仍驻留 | 5 | 原聊天输入框恢复可用 | 0.080 | 0.064–0.085 |
| 独立测试包，全新 Linux 环境和 DSH 配置 | 2 | 首次欢迎页的「继续」可点击 | 24.02 | 23.80–24.25 |

原版五次冷启动中，Android 报告的 Activity 首帧中位数为 0.140 秒。此时显示原生启动页，DSH 和网页仍在准备。空环境测试单独使用了一个包名；保留该测试包的 Android 和 WebView 数据，每轮在隔离的数据位置新建 Linux 环境。两次镜像检查、解包和发布分别为 11.21 和 11.17 秒，APK 安装及系统下载耗时均在计时之外。[Android 启动指标](https://developer.android.com/topic/performance/vitals/launch-time)

## 日常冷启动时间花在哪里

为手机现有安装临时加入时间探针，保留原镜像和配置。下表基于四次关闭编译缓存的冷启动，先计算每轮的阶段差，再汇总。各行中位数可能来自不同轮次。

| 阶段与边界 | 中位数 | 最短–最长 |
| --- | ---: | ---: |
| 桌面启动到 Activity 开始创建 | 0.119 | 0.094–0.124 |
| 检查、复用已展开的镜像 | 0.032 | 0.029–0.051 |
| 提交 Sucrune 执行到 Node 运行第一段用户 JS | 1.234 | 0.797–1.264 |
| 首段 JS 到 DSH 发出本地服务监听就绪通知 | 7.934 | 5.053–9.128 |
| DSH 发出通知到 App 读到登录交接文件 | 0.200 | 0.113–0.299 |
| 校验本地登录与主页并设置 WebView Cookie | 0.081 | 0.063–0.086 |
| 等待临时交接文件清理 | 0.111 | 0.105–0.122 |
| 创建 WebView | 0.043 | 0.035–0.046 |
| WebView 导航到聊天输入框可用 | 1.103 | 1.000–1.172 |
| **桌面启动到输入框可用，全程** | **10.866** | **7.621–12.075** |

Sucrune 复用 Android 内核。1.234 秒包含 Android 隔离 worker、原生 runner、客体 ELF 和动态库加载，以及 Node/V8 引导。四轮中，提交到系统记录 worker 已绑定只用 47–53 毫秒，中位数 51 毫秒。现有记录能区分这段和后续引导，不能单独给出纯 ELF 加载耗时。

## 后续启动为什么看不到「正在启动 Linux」

首次创建环境时，App 会显示「正在准备 Linux 环境」和解包百分比。以后冷启动时，App 先显示「正在检查 Linux 环境」；镜像收据匹配便直接复用，再显示「正在启动 DSH WebUI」。启动 Linux 客体和启动 Node 都发生在后一条提示期间。热返回则直接恢复已经加载的 WebView。若要让阶段更清楚，可在提交客体执行时显示「正在启动 Linux 运行环境」，进入 DSH 入口后改成「正在加载 DSH」。提示可以跟随实际进度切换，无需增加等待。[镜像复用](../app/src/main/kotlin/app/dsh/sugar/runtime/GuestImage.kt) · [当前启动流程](../app/src/main/kotlin/app/dsh/sugar/runtime/SugarRuntime.kt)

## 优化顺序

1. **优先剖析 DSH 启动到监听的 7.93 秒。** 下一轮可以在 profile 配置读取、模块解析、插件装配、HTTP 服务就绪处分别计时，再决定哪些非首页功能可等第一次使用时加载。本轮没有测到单个插件的成本。
2. **用通知代替每 300 毫秒轮询登录交接，把清理移出首屏关键路径。** 目前 App 从服务发出通知到读到文件，中位数要等 200 毫秒。凭据成功清零后，UI 仍会等第二个执行完成文件清理，中位数 111 毫秒。两处合计可争取约 0.2–0.3 秒，具体节省量需实现后复测。通知应先注册再检查文件，保留超时和失败清理。
3. **首装单独优化解包。** 根镜像展开 768,071,933 字节，共 44,678 个文件，对应 4,416 个不同的直接父目录。当前每个文件都会调用一次创建父目录，可以先试按目录去重，再测首次启动。同一份镜像的日常检查只需约 32 毫秒。
4. **当前版不宜直接打开 Node 编译缓存。** 单独的调试训练轮在服务发出监听通知后主动刷新缓存，没有到达可操作输入框。专用缓存目录里有 1,003 个临时文件，全为零字节，因此没有可比较的热缓存数据。Node v24.22.2 的这条写盘路径用 libuv 做指定偏移的向量写入；当前 ARM64 客体缺少对应的 `pwritev`（系统调用 70）。写入失败是有源码依据的解释，登录失败当时的具体 errno 没有捕获。先用小用例验证并补齐该调用，再检查缓存内容和下一轮实际启动耗时。[Node 编译缓存实现](https://github.com/nodejs/node/blob/v24.22.2/src/compile_cache.cc#L419) · [libuv 写盘路径](https://github.com/nodejs/node/blob/v24.22.2/deps/uv/src/unix/fs.c#L427) · [Sucrune 系统调用处理](../../Sucrune/native/shell_runtime.c)

## 记录与复核

通过 ADB 发出带桌面启动参数的 Intent。这里的冷启动指进程已停止；手机未重启，系统文件缓存可能保留。计时从设备侧启动命令开始。WebView 的结束点是可见元素通过点击命中检测；不发送消息。每轮取三次 ADB 时钟样本，选往返最短的一次校准主机与手机时钟，设备 uptime 刻度约 10 毫秒。热返回约 80 毫秒，适合按数量级解读。

四轮分段统计与五轮原包用户体验统计分别保留。编译缓存实验后另有两轮关闭缓存的恢复检查，均进入原有输入框（11.43 和 13.68 秒）。首次空环境另有一轮校准测试未识别欢迎页按钮，已排除。已恢复测试前同一 SHA-256 的原 APK 并验证输入框可用；对应单轮为 8.77 秒，也不并入五轮基线。临时副本、启动探针及试验缓存均已移除。逐轮数据见[去敏测量 CSV](android15-startup-samples.csv)。
